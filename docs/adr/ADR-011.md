# ADR-011: Vite + React for frontend framework (not Next.js)

**Date:** 2026-04-12
**Status:** Accepted

## Context

The original design assumed the salesbot frontend would be a Next.js page within the arlabs.tech codebase — inheriting the existing framework, design system, and Vercel deployment. ADR-002 labelled the frontend module as "Next.js on arlabs.tech."

Then ADR-008 decided on a subdomain split: `salesbot.arlabs.tech` served by Caddy on the Contabo VPS, separate from the portfolio site on Vercel. Once the salesbot lives on its own subdomain and its own server, the original rationale for Next.js evaporates — there's no arlabs.tech codebase to inherit from.

The salesbot frontend is a single-page client-side voice interface. It has:
- One page (no routing)
- No server-side rendering needs (no SEO — it's a live demo, not indexable content)
- No API routes (the backend is a separate FastAPI service)
- No static generation (the page is interactive, not content)
- No image optimization (voice UI has no images)

The question is whether the overhead of Next.js is justified for a standalone SPA, or whether a lighter build tool is more appropriate.

## Decision

We will use **Vite + React + TypeScript + Tailwind CSS** for the salesbot frontend, as a standalone SPA at `projects/arlabs.tech/salesbot/frontend/`.

Vite provides:
- Fast dev server with HMR (sub-100ms hot reload)
- Simple static build output (`npm run build` → `dist/` with HTML/JS/CSS)
- Direct compatibility with Pipecat's own React examples and documentation
- Minimal configuration — no framework opinions about routing, data fetching, or server components

## Consequences

### What we give up vs Next.js

| Capability | Impact on salesbot | Mitigation |
|-----------|-------------------|------------|
| Server-side rendering | None — voice UI is entirely client-side, no SEO | N/A |
| File-based routing | None — single page, no routes | N/A |
| API routes | None — backend is separate FastAPI (ADR-006) | N/A |
| Image optimization | None — voice UI has no images | N/A |
| Preview deploys per PR | Already accepted as tradeoff in ADR-008 | GitHub Action to VPS if needed later |
| Vercel integration | Not applicable — salesbot is on VPS (ADR-008) | N/A |
| React Server Components | Not needed — all components are client-side with WebRTC | N/A |
| Middleware / rewrites | Caddy handles reverse-proxying to backend | Caddy config |

### Positive

- Smaller bundle — no Next.js framework runtime overhead for features we don't use
- Faster dev iteration — Vite's dev server is meaningfully faster than Next.js for HMR
- Simpler mental model — no distinction between server/client components, no `'use client'` directives
- Matches Pipecat SDK examples — less impedance mismatch when following their documentation
- Build output is plain static files — trivially served by Caddy, no Node.js runtime on VPS

### Negative

- If the salesbot ever needs multiple pages (e.g., admin dashboard, analytics), we'd need to add a router (react-router) or reconsider the framework choice
- No built-in middleware for auth or redirects — would need Caddy config or a separate solution
- Design tokens are not shared with arlabs.tech at the code level — the merged theme was manually ported from arlabs.tech's Tailwind config and the Dark Instrument theme reference

### Neutral

- This decision is reversible. The React components, hooks, and Tailwind classes would transfer to a Next.js app with minimal changes if the need arose.
- ADR-002's three-module architecture is unaffected — the Frontend module's internal framework choice doesn't change its interface with the LLM module (still `POST /api/rooms`).
