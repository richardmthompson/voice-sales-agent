# ADR-001: Build From Scratch vs. Deploy Existing Codebase

**Date:** 2026-04-04
**Status:** Accepted

## Context

The original salesbot is a 26K-line, three-application system (React frontend, FastAPI backend, Pipecat voice runtime) built by the Agent Flywheel in 4 days. Two approaches exist for getting a live voice demo on arlabs.tech:

1. **Deploy and iterate** on the existing codebase — get it running, then modify
2. **Build from scratch** — start at V0 (bare voice loop), use architectural insights from the original as a guide

The existing codebase has no deployment documentation that works out of the box. Previous attempts to reverse-engineer it produced architectural understanding (C4 Level 1 and Level 2 diagrams, comprehension documents) but no running system. The codebase was AI-generated without human comprehension of every line, making debugging and modification risky.

The goal is not just a working demo but a system where every line is understood and owned — a requirement for building in public and for long-term maintainability as a replicable voice AI backbone.

## Decision

We will build from scratch, starting at V0 (bare voice loop) and incrementing through versioned milestones. Each version is deployable and demo-able. The three-module architecture (Frontend, LLM, Voice) identified during C1/C2 analysis is carried forward from V0, but every line of code is written fresh.

Architectural insights from the original salesbot — the "Brain vs Body" separation, Pipecat pipeline ordering, Deepgram low-latency configuration, Daily.co room lifecycle — inform design decisions without being copied verbatim.

## Consequences

### Positive
- Every line of code is understood and owned by Richard — essential for building in public
- Incremental versions provide continuous demo-able progress rather than all-or-nothing deployment
- Simpler codebase at each stage means faster debugging and iteration
- Forced to make deliberate technology choices (documented as ADRs) rather than inheriting undocumented ones

### Negative
- Slower path to feature parity with the original 26K-line system
- Architectural insights from the original may be lost if not explicitly carried forward (mitigated by DESIGN.md "Known Gotchas" appendix)
- Some solved problems in the original codebase will need to be re-solved

### Neutral
- The original codebase remains available as reference material on the VPS (`infra/matrix/Projects/salesbot/`)
- V0 scope is deliberately minimal — the investment to reach a working demo is small
