# ADR-010: Daily.co region selection for geographically-distant audiences

**Date:** 2026-04-07
**Status:** Superseded
**Superseded by:** [ADR-019](ADR-019.md) (Pipecat Cloud handles bot-SFU co-location automatically)

## Context

The Voice module runs on a Contabo VPS in Lauterbourg, France. The first major demonstration of the salesbot is at GITEX AI Asia in **Singapore** — geographically far from the bot's hosting location.

A naive setup would route media as follows:

```
Singapore user's browser ──open internet──> bot in France ──open internet──> Singapore user's browser
```

Round-trip latency for this path is ~156ms (measured: WonderNetwork Strasbourg↔Singapore = 156ms RTT, France↔Singapore PEACE submarine cable = 136ms minimum). Adding network jitter, packet loss, and TLS overhead, the realistic media RTT for a Singapore user talking to a France-hosted bot over the open internet is ~180-220ms one-way.

In a typical voice agent's 1200ms turn budget (STT + LLM + TTS + transport), this geographic overhead consumes 15-20% of the budget — not fatal, but enough to make conversational flow feel sluggish at the margins. For a high-stakes live demo at a conference, this is not acceptable.

The hosting topology decision (ADR-008) deliberately keeps the bot on the Contabo VPS rather than migrating to a Singapore-region host. The reasoning: bot location is not the only — or even the primary — lever for voice latency in a Pipecat + Daily.co architecture.

### Daily.co's global media infrastructure

Daily.co operates a global private backbone with 75 PoPs in 10 geographic regions. P50 first-hop latency from a user to their nearest Daily PoP is 13ms (source: Daily.co engineering blog, July 2025). Daily handles routing between PoPs over its private backbone, which is faster and more reliable than open-internet routing.

Critically, **Daily.co supports region selection in its room creation API**. When creating a room via `POST /rooms` on the Daily REST API, the `region` parameter specifies which Daily region should host the SFU (Selective Forwarding Unit) for that room's media. Available regions include `us-west`, `us-east`, `eu-central`, `ap-south` (Mumbai), `ap-southeast`, and others.

When a Singapore user joins a Daily room with `region: 'ap-southeast'`:

```
Singapore user's browser
   │ ~13ms (first-hop)
   ▼
Daily.co Singapore PoP / SFU
   │ ~80ms (Daily private backbone)
   ▼
Voice module in Lauterbourg (subscribes to the SFU as another participant)
```

The user's media never traverses the open internet to France. The Singapore PoP holds the WebRTC connection to the user, and Daily's private backbone carries the media to the bot. Reverse path is the same.

This design **decouples bot geography from user geography**. The bot can run anywhere with reasonable internet — Daily handles the spatial optimization.

### Why this matters for the architecture decision

Without region selection, the only way to fix Singapore latency would be to move the bot to a Singapore-region host (Fly.io `sin`, Pipecat Cloud `ap-south` Mumbai, or a Singapore VPS). That's a real migration with cost, complexity, and ongoing operational burden.

With region selection, the fix is **a single API parameter**. We can serve audiences anywhere in the world from one Lauterbourg VPS, choosing the right Daily region per session.

This changes the long-term architecture story for the demo portfolio: **bot location is not a strategic question anymore.** It's a deployment convenience. Singapore audiences, US audiences, European audiences — same backend, different `region` parameter.

## Decision

We will use **Daily.co's `region` parameter** in the room creation API to place the media SFU in the geographic region closest to the audience for each session.

Concretely:

1. **The LLM module's `POST /rooms` endpoint** accepts an optional `region` parameter that is forwarded to Daily.co's room creation API.
2. **Default region:** `eu-central` (closest to the Lauterbourg bot, optimal for European users who are the largest expected audience).
3. **For GITEX (Singapore demo period):** override to `region: 'ap-southeast'` either by environment variable on the LLM module or by passing the region in the API call from the frontend.
4. **For future region-targeted demos:** the same parameter switch covers any audience location without changing infrastructure.

## Consequences

### Positive

- **GITEX latency problem solved with one API parameter.** No infrastructure migration, no second VPS, no temporary deploy.
- **Bot location becomes a deployment convenience, not a strategic decision.** We can serve global audiences from one VPS.
- **Reusable across the demo portfolio.** Every future demo gets the same region-selection capability for free.
- **Daily's private backbone is faster and more reliable than open-internet routing** between continents.
- **Per-session granularity.** Different sessions can use different regions (e.g., the same bot serving a European stakeholder call and a Singapore conference attendee within the same hour).

### Negative

- **Vendor coupling deepens.** This is now a third architectural dependency on Daily.co (alongside transport in ADR-004 and control plane in ADR-009). Switching to LiveKit or another provider would mean losing this capability or replacing it with that provider's equivalent.
- **The bot-to-LLM-API path is unchanged** by region selection. Claude API and ElevenLabs/Cartesia API calls still go from Lauterbourg over the open internet to wherever those providers are hosted. Region selection only optimizes the user-to-bot media path, not the bot-to-LLM API path. Total turn latency improvement is bounded.
- **Region availability is a Daily.co operational concern.** If Daily decommissions a region, our demo for that region's audience degrades to whichever region they fall back to.
- **The `region` parameter must be plumbed through.** The LLM module's room creation endpoint, the frontend's connect flow, and the deployment configuration all need to know about region selection. Additional surface area to maintain.

### Neutral

- Daily.co automatically picks an optimal region if none is specified, based on the user's geolocation. For most users this is good enough — explicit region selection is mainly for known-audience scenarios (a conference, a scheduled call with a specific person, an embedded demo on a region-specific landing page).
- This decision interacts with ADR-008: because the frontend is on the same VPS as the backend (and fronted by Cloudflare globally), the frontend latency is already optimized via Cloudflare's PoPs. ADR-010 closes the remaining gap on the audio path.
- This decision is reversible. If we ever migrate the bot to a Singapore-region host, the `region` parameter still works — we'd just default it to `ap-southeast` instead of `eu-central`.

## Notes

- Daily.co room creation API reference: `docs.daily.co/reference/rest-api/rooms/create` — `region` parameter.
- Daily.co engineering blog on global infrastructure (PoPs, P50 first-hop latency): July 2025.
- Measured baseline latencies: WonderNetwork Strasbourg↔Singapore = 156ms RTT; PEACE cable France↔Singapore = 136ms minimum.
- For GITEX preparation: validate `region: 'ap-southeast'` is currently provisioned by Daily.co before the event. Daily occasionally adjusts region availability.
- This decision does not preclude a future migration to a multi-region bot host (Fly.io, Pipecat Cloud) if voice latency becomes a binding constraint. Region selection is the V0/V1/V2 answer; per-region bot deployment is the V3+ answer when concurrent session counts justify it.
