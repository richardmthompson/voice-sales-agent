# ADR-017: Two-Gate Gamification Driving Pipeline UI

**Date:** 2026-05-26
**Status:** Partially Superseded by ADR-021
**Amended:** 2026-06-08, 2026-07-21

## Context

V1 introduced a two-gate discovery system (AI Landscape → Project Discovery) via system prompt engineering. The frontend pipeline rail advances based on message count — a placeholder that doesn't reflect actual conversation progress. V2 needs the pipeline UI to reflect real gate completions.

Three approaches were evaluated:

1. **LLM-only gates** — The LLM declares a gate complete in its response text. No code validation. Risk: LLM may declare a gate complete prematurely or inconsistently.
2. **Code-driven gates with decomposed tool calls** — Each finding (current_usage, tools, primary_use_case, aspirations) is a separate tool call. Guarantees completeness but forces the LLM into a mechanical pattern of discrete tool calls per data point instead of flowing naturally through conversation.
3. **Hybrid: LLM declares, code validates** — The LLM calls `complete_gate` with all findings. The handler validates required fields are present and non-empty. Returns success or a validation error listing missing fields.

## Decision

We will use two explicit gates (AI Landscape, Project Discovery) with a hybrid LLM-declares/code-validates pattern. The `complete_gate` tool accepts a gate identifier and a findings object. The handler validates required fields per gate.

**The `GATES` registry is the single source of truth for gate definitions.** It maps gate id → required fields (with descriptions). Both the validator and the system prompt derive from this one structure:

- The **validator** iterates the registry's required-field keys to check findings.
- The **system prompt** is rendered from the registry at startup — field guidance is generated, not hand-duplicated.
- **Error messages** on validation failure cite the registry's field descriptions.

Current registry entries:

- **AI Landscape** (`ai_landscape`): `current_usage`, `tools`, `primary_use_case`, `aspirations`
- **Project Discovery** (`project_discovery`): `problem`, `implication`, `vision`, `link`, `experience`

Adding a gate = adding a registry entry. The handler, prompt, and error messages pick it up automatically.

On success, the handler updates in-memory state and returns confirmation to the LLM. Background tasks write to SQLite and send an RTVI message to advance the frontend pipeline rail.

## Consequences

### Positive

- Pipeline UI reflects real conversation progress, not placeholder message counts
- Code validation prevents premature gate completion — the LLM must gather all required information
- Natural conversation flow preserved — the LLM accumulates findings conversationally, then makes a single tool call per gate
- Stepping stone toward full SPIN gamification in V3

### Negative

- Two gates is a simplification of the full SPIN methodology — nuanced qualification signals are not captured until V3
- Validation is structural (field presence), not semantic (field quality) — the LLM could pass low-quality data. Semantic validation deferred to V3's evaluation framework.
- ~~Gate definitions are hardcoded — adding or modifying gates requires code changes~~ *(Resolved by amendment: gate definitions are data in the `GATES` registry; adding/modifying gates is a data change, not a code-structure change)*

### Neutral

- Full SPIN methodology (Situation → Problem → Implication → Need-payoff) is deferred to V3, contingent on V2 plumbing being proven stable
- The `complete_gate` tool schema serves as the contract between conversation intelligence (LLM) and data infrastructure (code) — this boundary will persist into V3+

## Amendment — 2026-06-08

**What changed:** Gate definitions are now data-driven via a `GATES` registry (single source of truth), not hardcoded. The system prompt is rendered from the registry at startup; the validator and error messages also derive from it. This resolves the "hardcoded" negative consequence above.

**Why:** Preserves SSOT — gate field requirements were going to exist in three places (prompt prose, validation code, this ADR) with no enforced sync. Making the registry authoritative and rendering the prompt from it means one edit propagates everywhere. This is also the V3 forward-compat lever: V3's SPIN re-framing adds registry entries and swaps prompt templates — data + prompt changes, not a handler rewrite.

## Supersession Note — 2026-07-21

ADR-021 supersedes the single final `complete_gate` / `complete_<gate>` commit
mechanism. Live testing established that the responder can record findings incrementally
through a repeatable `record_<gate>` tool while code decides completion over accumulated
state. The two-gate product model, the `GATES` registry, and the code-validation
principle remain accepted.
