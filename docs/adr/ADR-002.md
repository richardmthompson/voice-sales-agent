# ADR-002: Three-Module Architecture (Frontend, LLM, Voice)

**Date:** 2026-04-04
**Status:** Superseded by [ADR-013](ADR-013.md) (Pipecat native tool calling over Agent SDK)

> The system is two containers, not three: a Vite + React page ([ADR-011](ADR-011.md)) and the Pipecat voice server, with the model running inline in the voice pipeline and no separate LLM module ([ADR-013](ADR-013.md)), plus SQLite for storage ([ADR-015](ADR-015.md)). DESIGN.md, "Architecture", describes the current structure. The decision below is kept as it was made.

## Context

The AR Labs Voice Agent needs to handle three fundamentally different kinds of work:

1. **Showing** — rendering UI in the browser (React, runs on client)
2. **Thinking** — deciding what to say (LLM calls, conversation logic, runs on server)
3. **Hearing and speaking** — real-time audio processing (STT, TTS, VAD, runs on server)

These have different performance characteristics. The audio pipeline is microsecond-sensitive and must never block. LLM inference tolerates tens of milliseconds of overhead. The frontend runs entirely in the browser. Mixing audio processing with blocking LLM calls or database writes in a single process would violate the latency constraints of voice interaction.

At V0 scope (bare voice loop with no conversation engine), the system is simple enough to run as a single process. The question is whether to start with a monolith and split later, or start with the right separation from the beginning.

Alternatives considered:
- **Monolith:** Single FastAPI process handling everything. Simpler deployment, but audio and LLM compete for the event loop. Refactoring to separate them later requires rearchitecting every integration point.
- **Two-service split:** Frontend + combined backend. Reduces the separation-of-concerns benefit — voice pipeline latency is still coupled to LLM processing time.

## Decision

We will maintain three separate modules from V0: Frontend (Next.js on arlabs.tech), LLM (FastAPI server), and Voice (Pipecat process). The Voice module handles hearing and speaking. The LLM module handles thinking. The Frontend handles showing.

The Voice module never decides *what* to say — it sends transcribed text to the LLM module and receives the response to synthesise. This keeps the latency-sensitive audio path free of blocking logic.

The three-module split was validated by the original salesbot architecture (three separate applications with the same responsibility boundaries) and is consistent with Pipecat's recommended deployment pattern.

## Consequences

### Positive
- Audio pipeline latency is isolated from LLM processing time — the dominant quality attribute for voice interaction
- Each module can be developed, tested, and deployed independently
- Conversation logic (LLM) can grow in complexity (RAG, state management, qualification scoring) without touching the audio pipeline
- Frontend can evolve UI (transcript display, visualisation) without backend changes
- Matches the original salesbot's proven architecture, reducing design risk

### Negative
- More deployment complexity at V0 than a monolith would require (three processes instead of one)
- Inter-module communication adds network latency (HTTP calls between Voice and LLM)
- Requires defining interface contracts between modules from the start

### Neutral
- The LLM module is thin at V0 (system prompt, single Claude call) but the boundary exists for future growth
- All three modules run on the same VPS in V0 — the separation is logical, not physical infrastructure
