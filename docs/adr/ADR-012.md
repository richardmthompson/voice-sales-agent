# ADR-012: Cartesia for text-to-speech

**Date:** 2026-04-07
**Status:** Accepted

## Context

The voice pipeline needs a TTS provider to synthesise the bot's responses into speech audio. Two candidates were evaluated:

1. **ElevenLabs** — used by VOX voice server, known quality, Richard's voice clone already exists there. Higher latency (~400ms first audio), higher cost per character.
2. **Cartesia** — Pipecat quickstart default, streaming-first architecture, lower latency (~150ms first audio), lower cost. Supports voice cloning.

The dominant quality attribute for a voice conversation is latency. Every millisecond between the user finishing their sentence and hearing the bot's response matters. TTS is one of the largest latency contributors in the pipeline (alongside LLM inference).

## Decision

We will use **Cartesia** as the primary TTS provider. Richard's voice clone has been configured in Cartesia (registered 2026-04-07).

ElevenLabs remains available as a fallback (API keys in both PAI `.env` and VPS `.env`). If Cartesia's voice quality proves insufficient for the production demo, the swap is a single-line change in `bot.py` (replace `CartesiaTTSService` with `ElevenLabsTTSService`).

## Consequences

### Positive
- Lower first-audio latency (~150ms vs ~400ms) — directly improves conversational feel
- Pipecat's quickstart and examples use Cartesia — less friction during development
- Streaming architecture means audio starts playing before the full response is synthesised
- Lower cost per character at scale

### Negative
- ElevenLabs has more mature voice cloning (wider emotional range, more fine-grained control)
- Cartesia is a newer provider — less community knowledge, smaller support ecosystem
- Richard's ElevenLabs voice clone may sound better than the Cartesia clone (subjective — needs A/B testing)

### Neutral
- The Pipecat pipeline abstracts the TTS provider behind a common interface — swapping providers requires changing one service class, not restructuring the pipeline
