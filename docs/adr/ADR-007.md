# ADR-007: Conversation Orchestration Approach

**Date:** 2026-04-05
**Status:** Proposed

## Context

The LLM module needs a way to manage conversation state and orchestrate LLM calls. At V0, this is trivial — a single Claude API call with a system prompt, no state management. But from V3 onwards (conversation memory within session) and especially V4+ (SPIN selling methodology, qualification scoring, RAG), the module needs structured conversation orchestration.

The question is what orchestration approach to adopt:

| Approach | Description | Complexity |
|----------|-------------|------------|
| **LangGraph** | Graph-based state machine for LLM workflows. Nodes are processing steps, edges are transitions. Built-in checkpointing, human-in-the-loop, and streaming. | Medium-high — powerful but adds conceptual overhead and dependency |
| **Custom state machine** | Hand-rolled Python state management — conversation phases as an enum, transitions as explicit code | Low-medium — full control, no dependencies, but must build checkpointing and error handling manually |
| **Other frameworks** (CrewAI, AutoGen, etc.) | Multi-agent orchestration frameworks | High — designed for agent-to-agent coordination, overkill for single-agent conversation management |
| **Plain Claude API** | Direct Anthropic SDK calls with conversation history in memory | Minimal — sufficient for V0-V2, insufficient when conversation phases and scoring are needed |

The original salesbot used LangGraph for its conversation engine, including SPIN selling phase transitions and checkpoint persistence via `langgraph-checkpoint-sqlite`. This validates LangGraph's applicability but does not mean it is the right choice for a fresh build — the original was AI-generated and its LangGraph usage was not manually validated for correctness or simplicity.

Research is needed to evaluate whether LangGraph's graph model is the right abstraction for SPIN selling phases, or whether a simpler state machine would suffice with less dependency overhead.

## Decision

**This decision is deferred.** V0 proceeds with plain Claude API calls (direct Anthropic SDK). The orchestration approach will be decided when conversation state management is needed (V3 planning phase).

Research questions to resolve before this ADR is accepted:
1. Does LangGraph's graph model naturally express SPIN selling phases and transitions, or does it add incidental complexity?
2. What is the minimal LangGraph setup for conversation state with checkpointing — is it simpler than a hand-rolled solution?
3. Are there lighter alternatives that provide state persistence without full graph orchestration?
4. **Cross-session resume-after-disconnect requirement** (added 2026-04-07). A dropped voice call mid-conversation should not lose accumulated qualification state — the user clicks Connect again and resumes where they left off. This requires: (a) user identification (browser cookie + email captured in the first call as fallback), (b) a compact structured conversation state object persisted to a store (SPIN stage, qualification signals, topics covered, commitments made), and (c) restoration of that state into the LLM context on reconnect. This requirement is a **soft vote for state-machine-style orchestration** because the compact state object maps cleanly to "current node + accumulated context" in a state-machine model, and less cleanly to freeform conversation history. The failure cost is asymmetric across the conversation: dropping at second 5 is fine, dropping at minute 8 just before booking loses the lead entirely. See V3 row in `DESIGN.md` Version Progression table for the feature scope.

## Consequences

### Of deferring

### Positive
- V0 ships with minimal dependencies — no orchestration framework to learn, configure, or debug
- The plain Claude API call is the simplest possible implementation, reducing V0 risk
- Decision is made with more information — by V3, we will have hands-on experience with the voice pipeline and conversation patterns

### Negative
- When orchestration is introduced (V3+), it may require restructuring the LLM module's endpoint internals
- The DESIGN.md C2 diagram currently shows "LangGraph" — this is aspirational, not decided. Must be noted as provisional

### Neutral
- The LLM module's external interface (`POST /process`) remains the same regardless of internal orchestration — the Voice module is unaffected by this decision
- If LangGraph is adopted later, the LLMProcessor in the Voice module still calls the same HTTP endpoint
