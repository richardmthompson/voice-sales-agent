# ADR-020: pipecat-flows for Conversation State Machine

**Date:** 2026-06-12
**Status:** Accepted
**Amended:** 2026-07-21

## Context

V2 needs the conversation to be a structured progression — discrete gates (AI Landscape, Project Discovery, Close) that the bot moves through, recording structured findings and advancing the frontend pipeline rail as each completes. ADR-013 settled that tool calling happens natively in-process on `OpenAILLMService` (no Agent SDK). What it did not settle is *who tracks conversation state* — ADR-007 (Conversation orchestration) has sat "Proposed" since the original design.

Two paths were on the table (impl-notes Decision Log, D1):

1. **Hand-built gate logic** — a `session_state.py` dataclass, a `complete_gate` handler registered via `llm.register_function`, and prompt prose describing the phases. State and validation hand-maintained.
2. **pipecat-flows** — the official Pipecat library for structured conversation. The conversation becomes a state machine of `NodeConfig` nodes; the LLM moves between them by calling functions; each node exposes only its own prompt and tools. A `GATES` dict acts as single source of truth, generating both the node prompt and the function schema so questions and validation cannot drift.

pipecat-flows is the cleaner design, but it carried one hard, untested risk: **`FlowManager` and the RTVI machinery had never been combined.** The frontend pipeline rail depends on RTVI `ServerMessage` delivery (ADR-009). If FlowManager conflicted with RTVI at the frame level, the whole pivot collapsed. Nothing else was safe to build until that was proven.

## Decision

We adopt **pipecat-flows** as the V2 conversation orchestrator, resolving ADR-007. The conversation is modelled as `NodeConfig` nodes; transitions happen when a node's `FlowsFunctionSchema` handler returns the next node; the `GATES` dict generates nodes (prompt + schema) so the two never diverge. This is a state-machine layer *on top of* ADR-013's native tool calling — it adds no separate process and no Agent SDK, so ADR-013 stands.

This is gated on — and now confirmed by — the coexistence spike **PAI-9ji.2.1.1**. A throwaway 2-node auto-driving flow proved all three checkpoints against installed `pipecat 0.0.108` + `pipecat-ai-flows 0.0.24`:

1. **BOOT** — a pipeline with both the auto-wired RTVI processor/observer and an initialised `FlowManager` started without error and spoke its first node.
2. **TRANSITION** — the LLM called the node's function and `FlowManager` advanced node A → node B.
3. **RTVI DELIVERY** — a custom `ServerMessage` fired from inside a flow handler arrived at the React client's console (`{action: "spike_ping", from: "node_a"}`).

API facts established by the spike: `FlowManager` takes `task=` (a `PipelineTask`), not `worker=`; `PipelineTask(enable_rtvi=True)` (the default) auto-creates both the RTVI processor and its observer; a handler reaches the channel via `flow_manager.task.rtvi.send_server_message(data)`; `FlowManager` consumes the context-aggregator *pair*, not the unpacked tuple.

## Consequences

### Positive

- Conversation state is real and code-owned (in `flow_manager.state`), not prompt-only — replacing the message-count proxy in `usePipelineStage.ts`
- `GATES` as SSOT means a node's questions and its validation schema are generated together and cannot drift
- Per-node tool/prompt scoping keeps the LLM focused on one gate at a time
- RTVI coexistence is proven, not assumed — the rail can be driven by real gate completions (ADR-009 + ADR-017 now have a confirmed delivery path)

### Negative

- Adds the `pipecat-ai-flows` dependency (pinned 0.0.24) and its node/handler concepts to the codebase's surface area
- Dynamic-mode transitions live in handler return values — flow logic is spread across node factories and handlers rather than one declarative table
- 0.0.x library — API churn is possible; the version is pinned in `uv.lock` to contain it

### Neutral

- Supersedes ADR-007 (Conversation orchestration — Proposed): pipecat-flows is that orchestrator
- Consistent with ADR-013 (native tool calling) — flows wraps it, no separate process introduced
- The spike code (`backend/voice/spike.py`) and the temporary frontend listener in `AppMinimal.tsx` are throwaway and to be removed once Slice 1 implementation begins; the spec `PAI-9ji.2.1.md` must be reconciled from the pre-pivot hand-built design to the flows design

## Amendment — 2026-07-21

ADR-021 changes the gate tool contract, not the orchestration decision. Gate nodes now
expose repeatable `record_<gate>` tools by default. Their handlers merge findings, let
`gate_is_complete` evaluate accumulated state, and return the next `NodeConfig` only
when complete. `FlowManager` still owns node activation and the flow topology remains
`ai_landscape → project_discovery → closing → wrap_up` — amended 2026-09-22 (vox-2cl.16.6.4, owner-ruled): `closing` now only mirrors and confirms, and the terminal `wrap_up` node speaks the goodbye and ends the call from its own post-action, removing the reliance on the model calling a close tool.

An evaluator-driven `set_node_from_config` path remains selectable for comparison, but
it is no longer the default gate transition mechanism.
