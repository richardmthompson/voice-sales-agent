# ADR-009: Real-time control plane via Pipecat RTVI / Daily data channels

**Date:** 2026-04-07
**Status:** Accepted

## Context

The salesbot frontend needs to display real-time data during a voice call:

- **Live transcript** — what the user just said (partials and finals), what the bot is currently saying
- **Audio visualizer** — waveform / level meter of the bot's voice
- **Status events** — connection state, "bot is thinking", "user is speaking", "bot is speaking", error states
- **Future custom data** — anything app-specific that doesn't fit the built-in RTVI catalog (e.g., a retrieved document, a structured form result, lip-sync visemes)

This data has to flow from the Voice module (running on the Contabo VPS) to the React UI (running in the user's browser) continuously throughout the call, with low latency.

There are three plausible transport mechanisms for this control plane:

| Option | Path | Tradeoffs |
|--------|------|-----------|
| **A. Separate WebSocket browser↔VPS** | Browser opens a second connection directly to FastAPI on the VPS | Familiar pattern; needs second TLS-wrapped WebSocket on the server; second auth surface; second reconnect logic; duplicates routing the WebRTC connection already provides |
| **B. Pipecat RTVI / Daily data channels** | Voice module emits messages via Pipecat's RTVI protocol; daily.co's WebRTC data channel carries them; the React app receives them via Pipecat's client SDK | Reuses the WebRTC connection that's already open for audio; same latency profile as audio; no extra connection; no extra auth |
| **C. Vercel rewrite proxy** | Browser → Vercel → VPS for control messages | Adds a hop on every message; turns Vercel into a real-time relay (not what it's designed for); irrelevant after ADR-008 since the frontend isn't on Vercel anyway |

The initial concern with Option B was that it might be a non-standard or experimental Pipecat usage that would create implementation risk. Research disproved this concern.

### Research findings

`RTVIServerMessageFrame` is a first-class, documented Pipecat primitive available since Pipecat 0.0.87 (current 0.0.102+). It is a `SystemFrame` that propagates immediately and bypasses queuing. Any `FrameProcessor` or pipeline event handler can push one. The browser side has an idiomatic React hook (`useRTVIClientEvent(RTVIEvent.ServerMessage, ...)`) and a vanilla JS callback (`onServerMessage`).

Most of the salesbot's control-plane requirements are satisfied by **built-in RTVI events** that require zero custom server code:

| Requirement | Built-in RTVI event | Client callback |
|-------------|---------------------|------------------|
| Live user transcript (partial + final) | `user-transcription` | `onUserTranscript` |
| Bot output text | `bot-output` | `onBotOutput` |
| User speaking state | `user-started-speaking` / `user-stopped-speaking` | `onUserStartedSpeaking` / `onUserStoppedSpeaking` |
| Bot speaking state | `bot-started-speaking` / `bot-stopped-speaking` | `onBotStartedSpeaking` / `onBotStoppedSpeaking` |
| Connection state | `bot-ready`, `error`, `transport-state-changed` | `onBotReady`, `onError`, `onTransportStateChanged` |
| LLM processing state | `bot-llm-started` / `bot-llm-stopped` | `onBotLlmStarted` / `onBotLlmStopped` |

The audio visualizer is computed entirely **client-side** from the WebRTC audio track via the Web Audio API. The `@pipecat-ai/voice-ui-kit` package (v0.8.2, March 2026) ships a `<VoiceVisualizer participantType="bot" />` React component that does this in one line. **No server involvement, no data channel traffic, no custom code.**

`RTVIServerMessageFrame` is only needed for genuinely custom application data — for example, sending a structured retrieval result to display in the UI, or per-frame lip-sync visemes (validated in production at GitHub issue pipecat-ai/pipecat#1516).

The Pipecat ecosystem ships an entire reference UI kit (`@pipecat-ai/voice-ui-kit`) including a `ConsoleTemplate` component that wires up transcript display, audio visualizer, and connection controls in approximately 10 lines of React. This is the canonical way to build a Pipecat client.

## Decision

We will use **Pipecat's RTVI protocol over Daily.co's data channels** for all real-time control-plane data flowing from the Voice module to the React UI. We will not open a separate browser-to-VPS WebSocket.

Concretely:

1. **Live transcript** — use the built-in `user-transcription` and `bot-output` RTVI events. Subscribe via `onUserTranscript` and `onBotOutput` in the React client.
2. **Audio visualizer** — use `<VoiceVisualizer participantType="bot" />` from `@pipecat-ai/voice-ui-kit`. Computed client-side from the WebRTC audio track. No server code.
3. **Speaking states / connection state / LLM events** — use the built-in RTVI event callbacks (`onUserStartedSpeaking`, `onBotStartedSpeaking`, `onBotReady`, `onBotLlmStarted`, etc.).
4. **Custom app-specific data** (when needed) — push `RTVIServerMessageFrame(data={...})` from a Pipecat processor on the server; receive via `useRTVIClientEvent(RTVIEvent.ServerMessage, callback)` on the client.
5. **No separate WebSocket** from the browser to FastAPI for any per-call data. The only browser-to-FastAPI HTTP request is the one-time `POST /rooms` to create the Daily room at session start.

## Consequences

### Positive

- **Idiomatic Pipecat.** This is the documented standard, used in production by other Pipecat-based products. We are not pioneering anything.
- **Reuses the existing WebRTC connection.** No second connection to manage, no second auth surface, no second reconnect logic, no second source of bugs.
- **Same latency as audio.** Control messages and audio frames travel through the same Daily.co data path, so transcript text and audio stay synchronized.
- **Most of the work is already done by Pipecat.** Built-in RTVI events cover transcript, speaking state, connection state, and LLM events without writing any server code.
- **Voice UI Kit gives us the visualizer for free** — `<VoiceVisualizer />` is one line.
- **No Vercel involvement in any per-call data path.** Compatible with ADR-008's hosting topology.
- **Easy to extend.** When V2/V3 introduces custom app data (lead scoring, qualification state, retrieved snippets), `RTVIServerMessageFrame` adds one type of message at a time without architectural changes.

### Negative

- **Vendor coupling to Pipecat + Daily.co.** Our control plane depends on Pipecat's RTVI protocol and Daily's data channel transport. Switching either out (e.g., to LiveKit) means rewriting the control plane. Mitigation: we already chose Daily.co (ADR-004) and Pipecat (ADR-003), so this is consistent with prior decisions.
- **`RTVIServerMessageFrame` is a `SystemFrame`** that bypasses normal pipeline queuing — meaning custom messages are NOT automatically synchronized with audio frames. For audio-aligned data (e.g., lip-sync visemes), timing alignment requires external coordination. Acceptable for status events, transcript display, and most app data — only matters for cases like avatar lip-sync.
- **Version sensitivity.** Requires Pipecat 0.0.87+ for `RTVIServerMessageFrame`, ideally 0.0.102+ for the full RTVI 1.0 standard. Requires `@pipecat-ai/client-js` 1.5.0+ for `onBotOutput` (current is 1.7.0). Requires `@pipecat-ai/voice-ui-kit` 0.8.2+ for the `VoiceVisualizer` component.

### Neutral

- This decision is reversible. If a future requirement genuinely needs a separate WebSocket (e.g., a control plane that must persist after the voice call ends, or coordination with a different backend), adding one is mechanical and doesn't break the data channel architecture.
- The `RTVIObserver` is registered automatically by `PipelineTask` unless we set `enable_rtvi=False`. We will leave RTVI enabled by default.
- The decision applies only to the Voice module → React UI direction. Browser → Voice module commands (e.g., mute, end-call) use the same RTVI mechanism in reverse via the client SDK.
