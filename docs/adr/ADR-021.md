# ADR-021: Responder-Driven Incremental Gate Recording

**Date:** 2026-07-21
**Status:** Accepted

## Context

The first V2 gate implementation exposed one `complete_<gate>` function per node. Its
schema required every gate field in one call. The conversational model therefore had
to conduct the conversation, retain and reconstruct the findings, decide that the gate
was complete, and initiate the transition. In live calls it often continued asking
questions instead, leaving `flow_manager.state` empty and the flow stuck.

A second, off-path evaluator was introduced to read the transcript after each turn,
extract findings, decide completion, and advance the flow with
`set_node_from_config`. Offline replay and live shadow traces proved that a focused
model call could perform the extraction. Making that evaluator authoritative then
introduced a different bug class: its background timing could start the next node over
an active exchange, and its completion judgement could infer fields the visitor had
not explicitly supplied.

The missing comparison was a responder with an incremental recording action. The
`PAI-2cl.11` experiment replaced the completion-only tool with an all-optional,
repeatable `record_<gate>` tool and made `gate_is_complete` the sole completion
authority. `PAI-2cl.12` then provided a `GATE_MODE` toggle for live side-by-side tests.
Responder mode completed both gates, populated state, respected turn-taking, and used
the normal Pipecat handler-return transition. Evaluator mode reproduced premature
force-advance, inferred completion, and talk-over.

## Decision

V2 gates use **responder-driven incremental recording** by default:

1. Each gate node exposes `record_<gate>` with every field optional.
2. The responder calls the tool whenever one or more useful findings emerge and may
   call it again to add or correct fields.
3. The handler sanitizes and merges accepted findings into
   `flow_manager.state[gate_id]`. Before merging, it applies the visitor-reply rule:
   nothing is recorded for a stage until the visitor has replied in it. The handler
   reads the conversation, finds the gate's window (everything after the latest
   instruction message carrying the gate's heading), and stores nothing unless a
   visitor message follows the bot's first spoken turn there. A refused call returns a
   neutral `recorded` result naming what was not recorded, why
   (`visitor_not_heard_in_phase`, or `conversation_unreadable` when the conversation
   cannot be read, in which case it fails closed), and a note telling the responder to
   ask. It is never an error result. This closes the 2026-08-02 shape, where a trailing
   answer to the previous gate's question filled the whole of the next gate
   (vox-2cl.14).
4. Application code runs `gate_is_complete` over the accumulated state.
5. An incomplete call remains on the current node and returns `({"status": "recorded", "gate": <gate_id>, "still_needed": [<field ids>]}, None)`: `still_needed` names the gate's fields not yet captured after this call's merge, by field id and in the `GATES` registry's order, so the responder never has to work out from its own earlier calls which answers are missing (vox-2cl.22). It comes from `fields_still_needed`, the function `gate_is_complete` is defined on (complete exactly when the list is empty), so the list and the completion decision cannot disagree. No stored value is echoed. A call whose values are all dropped by sanitising, including an empty call, carries the list too. Three replies carry no list: a refusal under the visitor-reply rule (item 3) keeps its `not_recorded`, `reason` and `note`; a completing call returns `{"status": "complete", "gate": <gate_id>}`; and once the close has been claimed (`_close_fired`, set by the graceful-exit tool or the closing stage's safety limit), or a forced move has left the gate (item 7), the incomplete reply is the bare `{"status": "recorded", "gate": <gate_id>}`, because nothing more will be gathered there.
6. A complete call emits persistence and RTVI events, then returns the next
   `NodeConfig` for `FlowManager` to activate. Two exceptions, both decided by
   `flow_nodes.gate_may_move_on`: once the close has been claimed the completion is
   persisted and announced but no next node is returned, and for a gate a forced move has
   left (item 7) it is persisted without the `gate_complete` message and no next node is
   returned, because the conversation is already past it.
7. **The forced move** is the one transition not made by a completed gate (vox-2cl.23).
   The per-stage safety limit counts exchanges, each a bot utterance followed by a
   visitor utterance in the stage, read from the stage's window at each settled turn; when a gate
   reaches 20 the recorder moves the conversation on to the gate's next stage and the gate
   stays incomplete. It sets the next node with `respond_immediately` false: the boundary
   follows a bot question the visitor has not answered yet, so the next bot speech is
   still the reply to a visitor line, made under the new node. The node entered carries
   an instruction to acknowledge that line and to read back anything said earlier that
   fits the new stage, asking one question to check it before recording; the
   visitor-reply rule (item 3) holds every write until the visitor has answered that
   turn. The browser is told with a `gate_moved_on` message, which the progress rail
   folds as a finished stage, while `gate_complete` keeps meaning every answer gathered.
   The closing stage's limit, 8 exchanges, still ends the call. After the move a
   background **rescue** (Richard's ruling 1 of 2026-10-27) asks evaluator mode's
   extractor, on the responder's model and with a prompt grounded in the visitor's own
   words, for the stalled gate's unrecorded answers, and writes only still-empty fields
   through the gate's record handler (item 3 applies); nothing waits for it, and it never
   speaks. The recording authority stays the record handler; the rescue is one more
   caller of it, at one moment.

`GATE_MODE=evaluator` remains available as a reversible comparison and diagnostic
path, but the evaluator is not the normal capture, completion, or transition authority.
Responder mode composes no evaluator at all (vox-2cl.16.5): the per-turn trace is
written by the recorder from the flow state, with no model call.

The closing node follows the same turn-respecting handler path. In responder mode the
responder calls `confirm_findings` once the visitor confirms the read-back, which moves
the flow to the terminal wrap-up node, and that node ends the call from its own
post-action (vox-l33, vox-2cl.16.6.4).

## Consequences

### Positive

- Findings become durable application state as they emerge rather than only at the end
  of a gate.
- Completion is deterministic and testable in code.
- Transitions stay inside Pipecat Flows' documented handler-return lifecycle.
- The active speaker and the transition share one turn boundary, avoiding background
  force-advance over the visitor. The forced move (item 7) is the one transition made
  from the recorder rather than a handler, and it is set without an immediate model run,
  so the bot's next speech still answers a visitor line.
- Corrections can overwrite an earlier field before the gate advances. After it advances, a later node's `correct_findings` tool overwrites a field the completed gate already holds, without moving the call (vox-2cl.9.4).
- The evaluator implementation remains available for future quality checks, question
  strategy, cross-gate analysis, or controlled comparison.

### Negative

- Tool calls occur on the voice path and can introduce a short pause.
- The responder may delay a recording call even when the information is available;
  prompts and model selection still affect capture cadence.
- Structural completion only proves that accepted fields are present. It does not
  guarantee that each answer is sufficiently specific or commercially useful.
- Beyond the visitor-reply rule, nothing in code checks that a stored value is
  something the visitor said. Once the visitor has replied in a gate, a model that
  invents the remaining fields completes it. The protection is the responder model and
  its prompts (ADR-022), measured on scored replays; code-checked quotes are deferred as
  vox-2cl.21.
- After a forced move the responder is told to use the visitor's earlier words. Code
  guarantees only the order (nothing is stored before the visitor has answered the
  bot's first turn in the new stage); whether the read-back is faithful and what is then
  recorded is model behaviour, measured on replays (vox-2cl.23).

### Neutral

- ADR-020 remains in force: Pipecat Flows is still the conversation orchestrator.
- ADR-013 remains in force: gate recording still uses native tool calling.
- This supersedes ADR-017's single final `complete_gate` / `complete_<gate>` commit
  mechanism, but retains its two-gate product model and `GATES` single source of truth.
- Historical evaluator specs remain valid records of the experiment, not the selected
  production authority.
