# ADR-013: Pipecat Native Tool Calling Over Agent SDK

**Date:** 2026-05-26
**Status:** Accepted

## Context

V2 requires tool calling for gate completion, conversation closing, and email triggering. The V0/V1 design (see ADR-002) assumed this would require extracting the LLM into a separate FastAPI endpoint using the Anthropic Agent SDK (`client.beta.messages.tool_runner()`). This assumption shaped the entire V2 architecture: a new container, an HTTP bridge between pipeline and LLM, and a new deploy target.

Research during V2 design interrogation revealed that Pipecat supports tool calling natively on the existing `OpenAILLMService`. Function schemas are registered on the service, tool handlers are defined inline in Python, and Pipecat manages the detect-execute-re-infer loop internally. The LLM sees tools in its system message and can call them; Pipecat intercepts the tool call, runs the handler, and feeds the result back to the LLM — all within the same pipeline process.

V2 tools are simple one-shot actions (mark a gate complete, end the conversation). They do not require multi-step autonomous workflows, parallel tool execution, or tool-use-within-tool-use patterns that would justify a separate orchestration layer.

## Decision

We will use Pipecat's native `OpenAILLMService` function calling with inline tool handlers for all V2 tools (`complete_gate`, `end_conversation`). The LLM stays inline in the pipeline. There is no separate LLM module, no `POST /process` endpoint, and no Agent SDK dependency.

This supersedes the V2 evolution note in ADR-002, which anticipated a three-container architecture. The system remains two containers (Frontend + Voice Server) plus SQLite storage.

## Consequences

### Positive

- Zero new infrastructure — no second process, no HTTP bridge, no new deploy target
- Lower latency — tool execution happens in-process, no network round-trip between pipeline and LLM
- Simpler debugging — single process, single log stream, single failure domain
- Pipecat manages the tool-call loop (detect → execute → re-infer) automatically

### Negative

- Tool handlers run in the voice pipeline process — a blocking handler would stall audio
- If V3+ tools require multi-step autonomous execution, the architecture will need revisiting
- Tighter coupling between pipeline and tool logic (acceptable for V2 scope)

### Neutral

- The Anthropic Agent SDK remains a valid option for V3+ if tool complexity grows (SPIN methodology, cross-session memory, booking flows may require orchestration)
- ADR-006 (FastAPI for LLM module) is superseded — the separate LLM module it assumed was never built; see [ADR-006](ADR-006.md) supersession note
- ADR-007 (Conversation orchestration) remains Proposed — Pipecat tool calling is not a conversation orchestrator, it's a tool execution mechanism
