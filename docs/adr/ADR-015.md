# ADR-015: SQLite for Persistent Storage

**Date:** 2026-05-26
**Status:** Accepted

## Context

V2 collects structured prospect data (gate findings, conversation transcripts, email addresses) that must survive past the voice session. V0/V1 has no persistence — conversation data exists only in memory during the call, with JSON file logging as a debug aid.

V2 storage requirements: queryable, reliable, able to associate emails with conversations, and writable from async background tasks without blocking the voice pipeline.

Four options were evaluated:

1. **Airtable** — Beautiful viewing UI, spreadsheet-like interface. Adds 200-500ms HTTP latency per write (mitigable with async pattern), limited to 1,000 records on free tier, stores data on US third-party servers.
2. **Supabase/Postgres** — Full relational database with real-time subscriptions. Production-grade but significant infrastructure for V2 volume (single-digit conversations per day initially).
3. **SQLite** — Local file database on VPS. Zero infrastructure overhead, fully controlled, queryable via SQL.
4. **JSON files** — Current approach for conversation logging. Not queryable, no identity linkage, not structured.

## Decision

We will use SQLite on the VPS with gate completions as the write trigger. Two tables: `prospects` (identity — name, email, company) and `conversations` (session data — transcript, summary, gate findings, email sent status).

Gate completions (see [ADR-017](ADR-017.md)) are the natural persistence boundary. When the `complete_gate` handler validates and accepts a gate's findings, it writes them to SQLite as a background `asyncio.create_task` — the voice pipeline never blocks on storage I/O. Each gate write is an incremental upsert: Gate 1 creates the record with AI Landscape findings, Gate 2 appends Project Discovery findings to the same record.

If no data exists for a session, the caller either didn't engage long enough to pass the first gate or is a new visitor who bounced. Both cases are equivalent from a storage perspective — no gate completion, no write, no noise in the database.

## Consequences

### Positive

- Zero infrastructure overhead — no separate database server, no connection pooling, no managed service
- Fully controlled — data stays on our VPS, no third-party data storage concerns
- Queryable — SQL for ad-hoc analysis, unlike JSON files
- Free — no per-record or per-request costs
- Fast for V2 volume — single-writer is fine for single-digit concurrent sessions

### Negative

- Single-writer limitation — WAL mode supports ~50-100 concurrent readers but only one writer. Will need migration to Postgres if concurrent sessions exceed this
- No built-in replication — VPS failure loses the database (mitigable with periodic backups)
- No viewing UI out of the box — Richard queries via SQL. Dashboard deferred to post-V2.

### Neutral

- Migration path to Postgres exists via SQLAlchemy or raw SQL export — the schema is simple enough that migration is a half-day task
- Airtable remains viable as a supplementary viewing layer if a dashboard becomes urgent — it can be fed from SQLite via a sync script
